# 文档索引

SnapOCR 的开发文档统一为**四份**，按“需求 → 设计 → 开发 → 完成情况”组织：

| # | 文档 | 职责 | 何时更新 |
|---|------|------|----------|
| 1 | [需求文档](01-需求文档.md) | 产品定位、用户场景、功能需求与编号（F-xx/N-xx）、快捷键、非功能需求、验收标准 | 需求增删改时（范围最高权威） |
| 2 | [设计文档](02-设计文档.md) | 架构、模块契约、线程/坐标模型、捕获/覆盖层/标注/OCR/系统集成方案、技术选型（附录 ADR） | 架构或接口契约变化时 |
| 3 | [开发文档](03-开发文档.md) | 环境要求、构建/运行/打包/CI、仓库结构、开发规范、阶段 0/一/二/三任务分解与并行分工 | 工具链、流程或任务变化时 |
| 4 | [完成情况](04-完成情况.md) | 里程碑状态、已完成内容与验收证据、需求实现状态、未完成工作 | 每次合并、里程碑完成后 |

## 权威顺序

1. **需求文档** —— 功能范围与验收标准的最高权威；
2. **设计文档** —— 架构与技术契约；
3. **开发文档** —— 环境、构建、规范与任务；
4. **完成情况** —— 实际状态与证据，不得夸大或提前勾选。

> `AGENTS.md` / `CLAUDE.md` 是 Agent 协作入口，内容服从四份文档；**不要另建第五份开发文档**。

## 维护规则

- 需求变化：先改需求文档，再同步设计/开发/完成情况，最后改代码与测试。
- 契约变化：先改设计文档（重大决策记录到 §17），再改实现。
- 任务变化：开发文档任务清单与完成情况状态同步更新。
- 每次合并：更新完成情况的验收证据与状态表；`README.md` 状态表保持同步。
- 图片等资源放在 `assets/`；文档内部使用相对链接，CI 前做链接检查。
- 文档文件名固定为 `01-需求文档.md`、`02-设计文档.md`、`03-开发文档.md`、`04-完成情况.md`。
